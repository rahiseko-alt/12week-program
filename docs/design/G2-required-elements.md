## 1. 各回が満たすべき必須要素（全7項目）

| # | 要素 | 満たしているとみなす条件 |
|---|---|---|
| 1 | 回番号 | 1から始まる連番で、欠番・重複が無い |
| 2 | **見出し** | その回で扱うテーマを表す15文字以上の文字列。**Q3 の測定対象はこの欄**である |
| 3 | 実施日 | 具体的な日付（YYYY-MM-DD）が入っている |
| 4 | 目的 | 20文字以上の文で、その回で何をするかが書かれている |
| 5 | 到達点 | 20文字以上の文で、終わりに何ができていれば合格かが書かれている |
| 6 | 所要時間 | 分単位の数値が入っている |
| 7 | 次回までの宿題 | 文字列が入っている（宿題が無い回は「なし」と明記されている） |

## 2. 回ごとに中身が違うこと（Q7が参照）

### 2-1. 番号の形を数え上げない

初版は「通し番号を取り除いてから回どうしを比べる」方式だったが、**番号の書き方を一覧で数え上げる**
やり方だったため、一覧に無い書き方を使えば12回まるごと同じ1文でも「全部違う」と判定された。
21通りの番号付けを試して**19通りが素通り**した（`1週目` `2日目` `Day1` `Week1` `STEP1` `No.1`
`#1` `【1】` `[1]` `＜1＞` `1/12` `パート1` `フェーズ1` `7月1日` ほか。basis-reviewer 7回目で実測）。
本製品は12週間のプログラムであり、`N週目` は最も自然な書き方である。数え上げでは塞げない。

そこで**番号を消すのをやめ、各回に固有の中身があるかを直接見る**。

### 2-2. 合格ライン

計画の全ての回について、次を満たすこと。

> その回の **見出し** に現れ、**他のどの回の見出しにも現れない**、
> **数字を除いた2文字以上の連続した文字列**が、**1つ以上ある**。

同じことを **目的** と **到達点** についても確かめる。

- 12回に同じ一文をコピーした計画は、番号の書き方が何であれ、固有のかたまりが1つも無いので落ちる。
- 各回で扱うテーマが違うまっとうな計画は、その回にしか出ない語（例：第2回だけの`ベースライン`）が
  あるので通る。

### 2-3. 数字を除く理由

`第1回の現状把握` と `第2回の現状把握` は、数字を含めれば `1` `2` が固有のかたまりになってしまう。
**比較の前に、対象文字列から算用数字（半角・全角）・漢数字・丸数字・ローマ数字をすべて取り除く。**
数字以外の文字は一切加工しない（削除も置換もしない）。

## 3. 課題が違えば中身が変わること（Q3が参照）

### 3-1. 測り方＝削除ではなく「出現」を見る

**2つの計画の文字列が違うかどうかでは測らない。** その方式は向きが逆で、課題の言葉を素直に
使い分けた良い実装ほど不合格になり、入力を読まない固定テンプレートが合格する
（basis-reviewer 6回目で実測）。

**各計画が自分の課題の語を含み、相手の課題の語を含まないか**を見る。

### 3-2. 固有語の選び方

課題Aの固有語＝課題Aの本文に現れ、課題Bの本文には現れない**2文字以上の名詞句**を3つ。課題Bも同様。

**次の語は固有語に選んではならない（除外リスト）。**
どの課題の計画にも自然に現れる汎用語であり、これを選ぶとまっとうな実装が落ちるため
（basis-reviewer 7回目で実測：`出荷` を固有語に選ぶと、不良率改善の正しい計画が
「手直しが減ったことで出荷の遅れが解消したかを確認する」という自然な1行で落ちた）。

> 顧客 / 現場 / 改善 / 品質 / 課題 / 目標 / 数値 / 実績 / 確認 / 対策 / 原因 / 効果 / 体制 /
> 計画 / 手順 / 記録 / 共有 / 判断 / 受入 / 発注 / 開発 / 実装 / 納期 / 出荷 / コスト / 時間

固有語は**その課題の中心語**（それが無ければ課題が成立しない語）に限る。

### 3-3. 確かめること

各回の見出しを**1回ずつ個別に**検索する。**連結した文字列に対しては検索しない**
（連結すると、ある回の末尾と次の回の先頭にまたがって一致してしまい、誤って合格する）。

| # | 確かめること |
|---|---|
| 1 | 計画Aの見出しのうち、**異なる3回以上**に、課題Aの固有語のいずれかが出現する |
| 2 | 計画Aのどの回の見出しにも、課題Bの固有語が1つも出現しない |
| 3 | 計画Bの見出しのうち、**異なる3回以上**に、課題Bの固有語のいずれかが出現する |
| 4 | 計画Bのどの回の見出しにも、課題Aの固有語が1つも出現しない |
| 5 | 計画Aと計画Bの**同じ回番号どうしで見出しが完全一致する回が、全体の半数を超えない** |

**#1・#3 の「3回以上」と #5 が要である。** 出現を「1回でもあればよい」にすると、
12回のうち1行にだけ課題文を貼り、残り11回は完全な雛形という実装が合格する
（basis-reviewer 7回目で実測）。#5 はその実装を同回一致11/12で落とす。

### 3-4. 検証入力は誰が選ぶか

**課題文と固有語の選定は independent-verifier（作業した本人以外）が行い、選んだ文と語を evidence に残す。**
本人が選べると、自分の実装が通る文だけを選べてしまう。
また、**同じ課題文を2回続けて検証に使わない**。

### 3-5. 課題の選び方（2組を必ず両方行う）

| 組 | 揃えるもの | 変えるもの | この組で落とすもの |
|---|---|---|---|
| 組1 | 期間・回数 | 会社名・業種・課題 | 完全な固定テンプレート |
| 組2 | **会社名・業種**・期間・回数 | **課題だけ** | 業種をキーにした固定表 |

## 4. 開発チームの有無が効くこと（Q6が参照）

「あり」「なし」だけを変えた2件を作り、次の両方を確かめる。

| # | 確かめること |
|---|---|
| 1 | 「あり」の計画には、開発の依頼・受入を扱う回が**独立した回として1回以上ある**（見出しがその回の主題としてそれを示している） |
| 2 | 「あり」と「なし」で、**同じ回番号どうしの見出しが一致しない回が1回以上ある** |

#2 が要である。#1 だけだと「あり」のときに各見出しの末尾へ
`開発チームへ発注し受入する` という一文を機械的に足すだけの実装が合格してしまう
（basis-reviewer 7回目で実測）。`docs/design/G2-input-fields.md` 3-2節は
この項目を「**回の構成が変わる**」と定義しており、語を足すだけでは定義を満たさない。

判定に用いる語の一覧は independent-verifier が選び、evidence に残す。
第3-2節の除外リストは Q6 にも適用する。

## 5. 判定の考え方

- **文字数の下限（15文字 / 20文字）** は、中身の無い値を機械的に弾くための下限であり、
  内容の良し悪しを測るものではない。
- **全ての回**が対象。1回でも欠けていれば Q5 は不合格。
- この一覧に無い要素の有無は Q5 の判定に影響しない。
